# Related tooling and the actual OSS gap

Reviewed 2026-10-16 against the linked upstream documentation. This is a product/research capability matrix, not a claim that the other projects lack features we have not audited. Versions and APIs can change; pilot package versions are pinned in `requirements-research.lock.txt`.

| Tool or approach | What it already provides | What it does not settle for this project |
| --- | --- | --- |
| [scikit-learn TF-IDF + linear classifier](https://scikit-learn.org/stable/modules/feature_extraction.html), [Pipeline](https://scikit-learn.org/stable/modules/compose.html) | Mature sparse text features, standard estimators, composable fit/predict workflows. This is a real baseline and may be the best practical choice when lexical evidence suffices. | A generic pipeline does not by itself specify our task's source-group leakage rules, labeled-development budget, model/data fingerprints, threshold provenance, or paper run manifest. Those can be built around scikit-learn; we should not present a linear head as novel. |
| [Sentence Transformers](https://www.sbert.net/docs/sentence_transformer/usage/usage.html) | Efficient, reusable embeddings for classification and other tasks; direct `encode` API and many backbones. | Embedding availability does not itself decide the task label, split/threshold policy, or operating cost. Dedicated embeddings are a strong backend candidate and beat Gemma on the SMS pilot. |
| [SetFit](https://huggingface.co/docs/setfit/quickstart), [trainer reference](https://huggingface.co/docs/setfit/reference/trainer) | Few-label text-classifier training and saved inference models; it fine-tunes a Sentence Transformer encoder and fits a classification head. This is an end-to-end alternative, not a weaker version of our frozen-feature idea. | Our narrow possible contribution would be a backend-neutral, auditable comparison and deployment contract around it, not few-shot training itself. The recipe pilot gives SetFit a strong quality/latency point. |
| [MTEB](https://github.com/embeddings-benchmark/mteb/blob/main/docs/get_started/usage/get_started.md), [classification implementation](https://github.com/embeddings-benchmark/mteb/blob/main/mteb/abstasks/classification.py) | Standardized embedding-model evaluations across many tasks, including classification with a classifier trained on embeddings. It is the stronger choice for a broad embedding leaderboard. | Our proposed focus is application-defined binary judgments, source-aware data contracts, threshold operating points, deployment artifacts, and explicit cost/label budgets. We should integrate or reuse MTEB tasks rather than duplicate its leaderboard. |
| [Hugging Face Evaluate](https://github.com/huggingface/evaluate), [EvaluationSuite](https://github.com/huggingface/evaluate/blob/main/docs/source/evaluation_suite.mdx) | Standard metrics, comparisons, measurements, and composable evaluation suites. | Metric computation and suite execution do not automatically establish whether a task-specific dataset split is leakage-free, a threshold is legitimately selected, or an artifact reproduces a deployed score. We can reuse its metrics instead of inventing replacements. |
| This repository today | Historical injection reproduction plus SMS and recipe pilots; matched IDs and development-label budgets, pinned source archives, saved heads, recipe-cluster bootstrap, and aggregate reviewer audit. | No installable stable API, prospective locked tests, independent-machine reproduction, weight-byte pinning, full task matrix, or evidence of general method superiority. The current scripts are research prototypes, not an established replacement for the above libraries. |

## Falsifiable differentiator

The possible OSS contribution is an **auditable text-judgment workflow across interchangeable backends**: task/label and source-group specification; deterministic, leakage-checked splits; explicit fit/selection/test label accounting; model and data provenance; loadable task-specific artifacts; uncalibrated-score versus probability semantics; policy/threshold separation; and paired quality/cost reports generated from prediction manifests. Existing components cover most individual steps. We should demonstrate that one small package makes the *whole contract* easier to reproduce on at least two independent tasks than assembling ad hoc scripts, without losing the ability to use scikit-learn, Sentence Transformers, SetFit, or Gemma underneath. If a clean-machine user cannot reproduce the contract and compare backends with less effort and clearer audit evidence, this differentiator fails.

This is a **software/workflow hypothesis**, not a new frozen-feature method claim. The two exploratory pilots do not establish general backend superiority: MiniLM leads the SMS thresholded result, while Gemma leads recipe macro F1 but has an uncertain gap against much faster SetFit. See [pilot decision](pilot_decision.md). For a paper, a new prospective task matrix, independent usability/reproduction study, or original benchmark contribution would still be needed. Do not rebrand existing TF-IDF, embedding, or SetFit techniques as novel.
